# BUG 修复工作流

基于 SpecForge V3 `bugfix-workflow` 方法论，适配 TME Java 工程场景。强制执行**复现 → 定位 → 修复 → 测试 → 验证 → 报告**六步流程。

**Source**：融合自 SpecForge V3 `bugfix-workflow`，适配 TME 技术栈。

---

## 前置判断：这到底是不是 BUG？

在动手之前，先想清楚问题性质：

| ✅ 是 BUG | ❌ 不是 BUG |
|:--|:--|
| 代码行为与需求文档/AC 描述不一致 | 用户想要一个新行为（需求变更） |
| "登录应跳转首页，实际跳转 404" | "这个按钮能不能改成红色" |
| "计算金额应该精确到分，实际有误差" | "列表页能不能加一个搜索框" |
| "删除操作应该校验权限，实际没校验" | "加一个批量导出功能" |
| NPE / SQL 异常 / 状态机跳转错误 | 已有功能的行为调整 |

如果判断**不是 BUG** → 告诉用户，建议走 `specforge-feature-evolution`（增量变更）或 `specforge-feature-dev`（新功能）。

---

## 前置条件

1. 读取相关功能的需求文档和 AC（`documents/01-planning/features/{功能名}.md`）
2. 读取相关技术方案（如果存在）
3. 了解涉及的 Java 模块和代码文件

---

## 问题分级

### 简单问题 → 快速修复

**判断标准**：一眼看出问题在哪，改动 < 10 行，不涉及复杂逻辑。

**做法**：
1. 确认问题现象
2. 直接定位并修复
3. 跑相关测试防回归
4. 告诉用户改了什么、为什么

不需要写完整修复报告。

### 复杂问题 → 完整排查

**判断标准**：原因不明显、涉及多个模块/Service、逻辑复杂、可能影响其他功能。

走下面的六步完整流程。

---

## 完整修复流程

### 第一步：收集信息，复现问题 🔴

> **硬规则：没有复现，就不动代码。**

需要了解清楚：
- **在哪里**：哪个功能/页面/接口
- **怎么触发**：操作步骤越具体越好
- **期望 vs 实际**：AC 要求什么行为，实际发生了什么
- **辅助信息**：日志、异常堆栈、截图、请求/响应内容

如果信息不够复现 → 逐轮追问 1-2 个最关键的问题，不要一次甩一堆。

**Java 场景关注点**：
- Controller 层的请求参数、返回值
- Service 层的核心逻辑和异常处理
- Mapper 层的 SQL 执行
- 中间件状态（Redis/Nacos/RocketMQ/MySQL）

**复现成功后再进入下一步。复现不了就继续收集信息，不要猜测着改代码。**

### 第二步：定位根因

从现象出发逐层缩小范围：

```
现象（用户看到的）→ 接口层（Controller）→ 业务层（Service）→ 数据层（Mapper/Entity）
```

对照**"期望行为 vs 实际行为"**找逻辑分叉点：
- 优先检查最近改动过的代码（`git log --oneline -10` 查看最近提交）
- 检查复用模块和公共工具类
- 关注事务边界、锁范围、并发场景

找到根因后确认：**这个 BUG 的影响范围有多大？** 只影响当前场景，还是可能影响其他功能？

### 第三步：修复

**原则**：
- **最小改动**：只改必须改的，不动不相关的代码
- **复用优先**：优先使用项目已有的模式和工具类（`ResultMessage`、`BusinessRuntimeException`、`AssertUtil` 等）
- **明确原因**：每处改动都要清楚为什么改

**Java 场景常关注**：
- Service 层的 `@RequiredArgsConstructor + private final` 注入是否正确
- `TransactionTemplate` 事务边界是否完整
- `BusinessRuntimeException` 异常处理是否完整
- 并发场景下 `Redisson` 分布式锁是否正确使用
- MyBatis-Plus `delete_flag` 逻辑删除是否被正确过滤

如果有多种修复方案 → 列出选项、分析利弊、给推荐让用户决策。

### 第四步：测试验证

根据 BUG 性质选择验证方式：

| BUG 类型 | 验证方式 |
|:--|:--|
| **逻辑/数据类** | 写单元测试或集成测试覆盖此场景。**理想情况：测试在修复前失败、修复后通过** |
| **API 异常类** | 单元测试 + Postman/curl 验证 |
| **数据库问题** | 查询验证数据状态 + 单元测试 |
| **UI/交互类** | 浏览器端验证（截图/操作路径） |
| **并发问题** | 单元测试 + 压测模拟（如可行） |

无论哪种方式，**修复后必须跑一遍相关测试套件确保没有回归**。

### 第五步：生成修复报告

创建目录 `documents/02-review/bugfix/`（如不存在），生成修复报告：

```
documents/02-review/bugfix/{YYYYMMDD}-{HHMM}-{问题简述}.md
```

**报告结构**：

```markdown
# BUG 修复报告：[问题简述]

## 基本信息
- **发现时间**：YYYY-MM-DD HH:MM
- **影响功能**：{功能名}
- **严重级别**：P0/P1/P2/P3
- **关联 AC**：AC-XXX（若无则标注"无对应 AC，已建议补充"）

## 问题描述
- **现象**：用户看到什么 / 接口返回什么
- **期望行为**：AC 或需求文档规定的行为
- **实际行为**：实际发生的行为

## 复现步骤
1. {具体操作步骤}
2. ...

## 根因分析
{技术层面的根因，涉及的具体代码位置、逻辑缺陷}

## 修复方案
{改了什么、为什么这样改、涉及的文件}

## 验证结果
- 单元测试：{新增/修改了哪些测试，结果}
- 回归测试：{跑了哪些已有测试，结果}

## 影响范围
- 受影响的其他功能：{有/无}
- 是否需要同步更新文档：{是/否，哪些文档}
- 是否需要 DDL 变更：{是/否}

## 预防措施
- 是否需要补充 AC：{是/否}
- 是否需要补充测试：{是/否}
- 是否需要更新编码规范：{是/否}
```

### 第六步：同步更新

如果修复过程中发现代码行为与现有文档不一致：
- 更新 `documents/01-planning/features/{功能名}.md` 的 AC 或范围描述
- 更新 `documents/01-planning/features/{功能名}_技术方案.md` 的设计描述
- 如有 DDL 变更，同步更新 `documents/03-releases/` 下的 SQL 文件

---

## 底线规则

- **先判断是不是 BUG** — 需求变更不走 BUG 修复流程
- **复杂问题未复现不动代码** — 这是铁律，任何情况下不可违反
- **修复后必须有验证** — 自动化测试或实际验证，至少一种
- **复杂问题必须生成修复报告** — 简单问题不需要
- **最小改动原则** — 不顺手重构不相关的代码
- **修复测试先行** — 先写能复现 BUG 的失败测试，修复后测试通过
