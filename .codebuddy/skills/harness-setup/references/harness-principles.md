## 13 讲核心洞察摘要

### L01 — 强模型为什么在真实任务上失败
- 基准测试与真实工程之间存在能力差距
- 先修 harness，再换模型。Harness 投入产出比远高于换模型

### L02 — Harness 五子系统
- Harness = 指令 + 工具 + 环境 + 状态 + 反馈
- 五个子系统缺一不可。反馈子系统是投入产出比最高的部分

### L03 — 仓库即唯一真实来源
- Agent 只能访问仓库中的文件，其他地方的信息对 Agent 等于不存在
- 全新会话测试：新 Agent 只看仓库能回答 5 个问题才算合格
- ACID 原则：原子性(git commit) + 一致性(验证) + 隔离性 + 持久性(文件)

### L04 — 渐进式披露
- 入口文件 50-200 行，做"路由器"不做"百科全书"
- 专题文档按需加载，50-150 行/文档
- 利用"中间迷失"效应：重要信息放文件首尾
- 每条指令标注来源/适用条件/过期条件
- 拆分后成功率 45%→72%，安全约束遵循率 60%→95%

### L05 — 长任务连续性
- 状态持久化三件套：PROGRESS.md + DECISIONS.md + Git 检查点
- 强制上下班流程：上班读进度→下班记进度
- 有状态化将重建成本从 15 分钟降至 3 分钟（减少 78%）

### L06 — 初始化独立阶段
- 第一个会话只做初始化，不写业务代码
- 产出：可运行环境 + 可验证测试框架 + 启动就绪清单 + 任务分解 + Git 检查点
- 独立初始化的项目功能完成率比混合方式高 31%

### L07 — WIP 显式登记与范围表面
- 并行任务必须显式登记到看板（任务/阶段/状态/下一步/阻塞），切换前写回状态；建议同时进行 ≤3
- 范围表面外部化：DAG 结构 + 4 种状态(not_started/active/blocked/passing)
- VCR(验证完成率) < 1.0 时阻止新任务启动
- WIP 约束模式功能完成率 87.5% vs 无约束 37.5%（来源研究：有约束显著优于无约束）

### L08 — Feature List 是 Harness 基本单元
- 三元组：行为描述 + 验证命令 + 当前状态
- 状态机：not_started → active → passing（不可逆）
- 状态转移由 Harness 控制，Agent 不能自己改

### L09 — 防止早停
- 三层终止校验：语法(编译) → 运行时(测试) → 系统级(集成)
- 分离 Maker 和 Checker，不让自己给自己批作业
- 功能验证前禁止重构

### L10 — 端到端测试
- 端到端测试从源头上减少缺陷，改变 Agent 编码行为
- 架构规则可执行化：把设计意图变成自动化检查
- 面向 Agent 的错误消息：什么出了错 + 为什么 + 怎么修

### L11 — 可观测性属于 Harness
- 双层可观测性：运行时（系统做了什么）+ 过程（决策为什么被接受）
- 冲刺合同 + 评估评分标准 + OpenTelemetry 标准化
- 有完整可观测性比无可观测性效率高 3 倍

### L12 — 清洁状态
- 清洁状态是"做完"的硬性定义，6 项检查不全通过不算完成（含部署后/E2E 验证闭环）
- 双模式清理：即时清理(每会话) + 定期清理(每周)
- 12 周后新会话启动时间可减少 85%

### L13 — Loop Engineering
- 六大原语：自动触发、并行隔离、项目知识(Skills)、连接器、子 Agent 分离、外部状态
- 成熟度 5 级：Goal Runner → Scheduled → Multi-Agent → Self-Feeding → Fleet

## Harness 文件职责矩阵

| 文件 | 定位 | 目标行数 | 硬上限 | 加载时机 | 更新频率 |
|------|------|:--:|:--:|------|------|
| **MEMORY.md** | 项目认知+领域抽象+Auto Memory | 50-80 | 200 行 | 每次会话注入 | AI 自动追加 |
| **入口文件（AGENTS.md/CLAUDE.md）** | 着陆页+路由器 | 80-200 | 200 行 | 每次会话 | 规范变更时 |
| **PROGRESS.md** | 状态快照 | 40-60 | — | 上班必读 | 每次会话结束 |
| **DECISIONS.md** | 决策日志 | 50-80 | — | 上班必读 | 有新决策时 |
| **`.codebuddy/rules/*.md`** | 分层规则（MDC 格式） | 30-80 | 80 行 | 按 globs 按需 | 规范变更时 |
| **tech-traps.md** | 技术陷阱冷记忆 | 按需 | — | 涉及相关技术时 | 踩新坑时 |
| **session-handoff.md** | 会话交接模板 | 30-50 | — | 上班必读 | 每次会话结束 |
| **context-budget.md** | 上下文预算声明 | 20-30 | — | 参考 | 预算变更时 |

## 行业最佳实践融合

本 Harness 体系融合了四大主流 Coding Agent 的最佳实践：

| 实践 | 来源 | 融合方式 |
|------|------|---------|
| 六层记忆架构 | Claude Code | MEMORY.md + Auto Memory 自主写入 |
| MDC 格式分层规则 | Cursor | `.codebuddy/rules/` + YAML frontmatter |
| 上下文硬截断 | Codex CLI | context-budget.md + 入口/MEMORY 硬上限 |
| AGENTS.md 跨工具标准 | OpenCode | 入口文件内容通用 + 平台自动检测 |

## Harness 退化信号（何时需要重建）

| 信号 | 严重度 | 操作 |
|------|:--:|------|
| Agent 频繁违反编码规范 | 🔥 | 检查 AGENTS.md 约束是否清晰、是否被中间迷失 |
| 跨会话需要重复解释项目背景 | 🔥 | 检查 MEMORY.md 是否过时、启动链是否被执行 |
| Agent 过早宣布任务完成 | ⚠️ | 检查下班清洁检查（6 项）是否执行、WIP 显式登记是否写死 |
| 文档与代码不一致 | ⚠️ | 执行腐败检测（改代码未同步文档） |
| PROGRESS.md 数日未更新 | 🔵 | 检查下班流程是否被遵守 |
