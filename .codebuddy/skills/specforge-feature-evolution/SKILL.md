# 功能迭代变更管理

基于 SpecForge V3 `feature-evolution` 方法论，适配 TME Java 工程场景。处理功能开发中或完成后的增量修改——不是推倒重来，而是**就地修改 + 增量追加**。

**Source**：融合自 SpecForge V3 `feature-evolution`，适配 TME 技术栈。

---

## 前置条件

开始前检查该功能的已有文档：
- `documents/01-planning/features/{功能名}.md` — **必须存在**（需求文档）
- `documents/01-planning/features/{功能名}_技术方案.md` — 如果存在则读取
- `documents/01-planning/features/{功能名}_任务规划.md` — 如果存在则读取

最低要求是需求文档存在。如果连需求文档都没有 → 走 `specforge-feature-dev` 从头开始。

同时扫描相关 Java 代码文件，了解当前实现状态。

---

## 第一步：理解变更意图

通过自然对话搞清楚三件事：
1. **改什么**：用户想增加/修改/删除什么行为？
2. **为什么**：是业务需求变化，还是发现了设计缺陷？
3. **多大**：是小修小补还是伤筋动骨？

### 关键判断：变更规模

| 变更类型 | 占原功能比例 | 处理方式 |
|:--|:--|:--|
| **微调 (Tweak)** | < 15% | 直接增量变更 |
| **扩展 (Extension)** | 15% ~ 50% | 增量变更 + 新增 AC |
| **重构 (Refactor)** | 50% ~ 70% | 增量变更，谨慎评估 |
| **重做** | > 70% | **建议回退到 `specforge-feature-dev`** 走完整流程 |

如果变更超过原功能的 70%，直接告诉用户：*"这次变更涉及范围过大（超过原功能 70%），建议当作新功能走完整的需求→设计→编码流程，避免越改越乱。"*

---

## 第二步：影响分析（四维评估）

分析完成后向用户展示，确认无误后再动手修改文档。

### 需求层面

- 需要新增/修改/删除哪些 AC？（保持 Given-When-Then 格式）
- 用户交互流程有哪些变化？
- 范围界定需要调整吗（做/不做）？

### 技术层面

- 数据库：新增/修改表？新增/修改字段？索引变更？
- API：新增/修改 Controller 路由？Service 接口？DTO/VO 变更？
- 依赖：需要引入新的 Starter 或第三方库？

### 代码层面（如果已有代码）

- 哪些现有 Java 文件需要修改？
- 需要新增哪些文件（Entity/Mapper/Service/Controller）？
- 已有的单元测试会不会受影响？

### 任务层面（如果开发进行中）

- 已完成的任务是否受变更影响？（原则上已验收通过的任务不动）
- 还未执行的任务是否需要调整？
- 变更任务是插入到现有序列中，还是追加在后面？

---

## 第三步：增量更新文档

**核心原则**：就地修改 + 末尾追加变更日志。

### 更新规则

| 场景 | 更新方式 |
|:--|:--|
| 新增 AC | 插入对应分类（Happy Path / Edge / Business Rule） |
| 修改 AC | 原地修改，保留 AC 编号，追加变更说明 |
| 新增 API | 加到"API 设计"章节末尾 |
| 修改 API | 原地修改接口定义 |
| 新增/修改表 | 更新 DDL 草案 |
| 不受影响的内容 | **原样保留，不要重写** |

### 变更日志格式

每份被修改的文档末尾追加：

```markdown
---
## 变更日志 (Change Log)

### CR-{序号}: {变更标题} ({日期})
**变更类型**: {微调/扩展/重构}
**变更原因**: {用户描述}
**变更内容**:
- {具体变更项1}
- {具体变更项2}
**涉及文件**: {受影响的文档和代码文件}
```

### CR 编号规则

检查 `documents/01-planning/features/` 下已有的变更任务文件，CR 编号从 CR-001 递增。

---

## 第四步：生成增量任务计划

### 任务标准

与 `specforge-feature-dev` 的任务规划阶段一致：
- 每个任务有**验证标准**（TDD RED 阶段依据）和**通俗解释**
- 标注对应 AC 编号和技术方案章节
- 标注依赖关系（包括对已有任务的依赖）
- 任务编号从原任务规划最大编号之后继续

### 必须包含回归验证任务

**必须**增加至少一个回归验证任务：
```
Task-REGRESS: 回归验证（跑已有测试套件，确保变更未破坏原有功能）
```

### 产出文件

```
documents/01-planning/features/{功能名}_变更任务_CR-{序号}.md
```

文件结构：变更概述 → 影响分析 → 增量任务清单 → AC 覆盖确认 → 回归验证计划

---

## 第五步：执行变更任务

**本 Skill 只负责分析和规划，不写业务代码。** 产出变更任务计划后停止。用户调用 `specforge-feature-dev` 的编码实现阶段（阶段④）来执行这些增量任务。

---

## 底线规则

- 不推倒重写已有文档，只增量修改受影响的部分
- 已通过验收的任务和代码不得被删除或重写
- CR 编号在同一功能内连续递增
- 新增/修改的 AC 必须使用 Given-When-Then 格式
- 每份增量任务计划必须包含回归验证任务
- 变更范围 > 70% 时必须建议用户走新功能流程
- DDL 变更必须同步更新 `documents/03-releases/` 下的对应版本 SQL 文件
