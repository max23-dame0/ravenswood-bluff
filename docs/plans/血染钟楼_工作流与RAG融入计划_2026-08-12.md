# 血染钟楼：工作流与 RAG 融入计划（PLN-041）

> 日期：2026-08-12
> 说明：基于 D:\ravenswood-bluff（Alpha 1.2「觉醒之鸦」）现状梳理的差距分析与工作计划。
> 状态：**published**——2026-08-12 全量实施完成（657 测试全绿 + ruff 0 + 10/10 聚合 gate + mock 8 人局 game_over），任务板见 §9。
> 诉求来源（用户 2026-08-12）：把每次 agent 玩家的**决策/发言**都包装为一个工作流，并引入 RAG 检索**规则书 / 对局经验 / 网络玩家分析经验**等内容，减少大模型不按照规则乱发言的幻觉情况。

---

## 结论

项目的"RAG 雏形"和"工作流雏形"其实都已存在，要做的是把它们升级为真正的系统，而不是从零搭建。但**可行性核查（§5）发现两处关键纠偏**：① Faiss 稠密检索当前运行时实际不可用（依赖未装）；② 用户诉求聚焦玩家侧决策/发言，与计划原首选试点（说书人裁决）不同——落地顺序已按用户诉求重排（§7）。

## 一、现状盘点（已有基础）

| 能力 | 已有实现 | 缺口 |
|---|---|---|
| RAG 雏形 | `vector_memory.py`（Faiss 稠密检索）+ `shared_pool.py`（规则打分检索）+ 三层记忆 + `PlayerProfileStore` 跨局注入 | ⚠️ Faiss 依赖未装、单路检索、无分块、无持久化、无评测 |
| 工作流雏形 | 说书人工具注册表（6 工具 + `decision_ledger`）+ 受控 Agent（think→act loop）+ 不可变状态机阶段推进 | 编排是隐式的，无显式工作流定义/执行器/可观测性 |

## 二、差距分析

**RAG 侧，从"简易向量记忆"到"真 RAG"缺 6 件事：**

1. **知识源**：规则/角色知识散落在代码（`src/content/trouble_brewing_terms.py`）里，没有结构化知识库文档 → 无法建索引
2. **分块策略**：`add_text` 整段入库，无按规则条目/事件轮次的分块（项目有 2652 个 jsonl 对局数据 + 29163 个说书人评测样本，全是待建索引的语料）
3. **混合检索**：只有 Faiss 单路稠密，缺 BM25 稀疏路 + RRF 融合（SuperMew 那套已验证 Recall@5=0.97 的做法可以直接搬）
4. **持久化**：Faiss 索引在内存、重启即丢，metadata 不落盘（与项目"数据资产"定位不符）
5. **相关性门控**：检索结果直接拼 prompt，无阈值过滤、检索不到时无规则兜底
6. **评测体系**：无 recall@k/MRR 离线评测集，无法量化注入质量

**工作流侧，从"工具调用"到"显式工作流"缺 4 件事：**

1. **工作流定义层**：说书人裁决链路（`adjudicate_night_info → choose_distortion → deliver_verdict → review_balance`）是隐式调用链，无声明式节点/分支/并行描述
2. **执行器**：无统一 WorkflowEngine（节点调度、状态跟踪、超时重试、事件发布到 `event_bus`）
3. **可观测性**：`decision_ledger` 只记账，无执行轨迹（节点耗时/入参出参/失败点）
4. **回放评测**：无法对单条工作流路径离线重放（对齐 live/offline）

## 四、必须守住的硬约束（项目红线，融入时不能破坏）

1. **前缀缓存**：检索注入必须放在同局内逐 token 稳定的 `stable_context`，不能在 `act()` 内动态重算（D013/D014 已固化的约束）
2. **信息隔离**：所有检索结果注入前必须过 `MemoryToolsLike.is_sensitive` 过滤（恶魔/队友名单）
3. **说书人确定性**：真实信息计算永远走规则引擎，LLM/检索只能影响"是否扭曲 + 怎么扭曲"
4. **门禁**：476 全绿 + ruff 0 + format + `check_doc_health.py`，新代码必须配套单测（预计 30~50 个）

### 5.2 关键纠偏（计划文档原始版与实际情况的两处出入）⚠️

**纠偏 1：Faiss 稠密检索当前运行时实际不可用**

- `src/agents/memory/vector_memory.py` 存在且逻辑完整，但本机 `.venv` **未安装 faiss / numpy / rank_bm25**，`pyproject.toml` 亦无这些依赖 → `VectorMemory.search()` 每次返回 `[]`，`archive_phase_memory` 的向量摄入为空转。
- 结论：所谓"RAG 雏形已有"是**纸面断言**。落地第一步必须是补依赖（`faiss-cpu` + `rank_bm25`），或走**纯本地 BM25 稀疏路**（零模型依赖、mock 环境可用、embeddings 降级兜底）。
- 影响：Phase 1 的 3/4 项是硬前提，不是可选优化。

**纠偏 2：玩家侧已有相当强的防幻觉防线（计划文档未提）**

玩家侧防幻觉机制已存在且分层完整：

| 防线 | 位置 | 作用 |
|---|---|---|
| 合法性校验 | `DecisionEngine.normalize_decision` | LLM 返回的目标/动作必须落在 `legal_context` 内，非法即 fallback |
| 本地启发式 | `local_low_value_decision` | vote/nomination 走确定性启发式，不经 LLM |
| 兜底决策 | `fallback_decision` | LLM 不可用/非法时产出稳定合法动作 |
| 发言净化 | `_sanitize_public_speech_content` | 兜底/主路径发言统一过净化（防泄露/防越界） |
| 证据增强 | `augment_reasoning_with_evidence` | 决策 reasoning 只拼工作记忆中的合法证据 |

- 结论：玩家的"规则越界"幻觉**已经被结构性强约束挡住**；当前幻觉残余集中在**发言内容层面**（角色能力描述不准确、规则引用错误、策略建议越界），这正是 RAG 规则知识注入最有价值的地方。

### 5.3 用户诉求与计划原型的差异

| 维度 | 计划文档原始版 | 用户诉求（2026-08-12） | 调整 |
|---|---|---|---|
| 工作流试点 | 说书人裁决（首选） | **玩家侧决策/发言**每次包装为工作流 | §7 重排：先玩家侧 trace 包装，说书人裁决作 P2 |
| 知识源 | 规则 + 历史对局 | 规则书 + 对局经验 + **网络玩家分析经验**（新） | 网络经验为**新知识源**：项目内无语料，需人工/半自动整理，技术上复用规则索引管线 |
| 目标 | 可观测性 + 平衡性 | **减少 LLM 乱发言幻觉** | 优先级调整为：规则静态注入 > 检索注入 > 工作流化 |

## 六、两条主线的可行性结论

### 6.1 工作流化：可行，但必须是"包装非重写"

- `act_with_strategy → act → tool calling → normalize_decision → sanitize → 执行` 本身已是**隐式工作流**（含分支：草稿复用 / 本地启发式 / LLM / fallback）。
- **最大风险**：`act()` 是深度优化热路径——草稿复用（0 次 LLM）、三层前缀缓存（D013/D014 硬约束）、双超时预算、mock 行为测试（480+ 单测断言）。**重写 `act()` 会同时击穿 token 预算与既有测试**。
- 可行路径（按收益/风险排序）：
  1. **P0 执行轨迹层（trace）**：`act()` 入口/出口轻量包裹，记录节点耗时/入参出参/失败点，落盘 `data/agents/{player_id}/games/{game_id}/workflow_trace.jsonl`。收益最大、风险最小。
  2. **P1 说书人裁决声明式试点**：6 工具编排为显式 `Workflow` 数据类 + 小型 `WorkflowEngine`（确定性红线不破）。
  3. **P2 玩家侧声明式化**：把隐式分支声明为节点（`retrieve_context → plan_strategy → decide → validate → sanitize`）。

### 6.2 RAG 注入：必须化解与缓存约束的冲突

D013/D014 要求注入内容**同局内逐 token 稳定**（`stable_context`），而 RAG 动态检索天然逐轮变化。化解方案——**三类知识源分三条路**：

| 知识源 | 注入时机 | 缓存影响 | 防幻觉效果 |
|---|---|---|---|
| **规则书**（角色能力/边界/动作红线） | **setup 期一次**，进 stable_context | 零破坏 | ★★★★★ 最直接治"不按规则乱发言" |
| **对局经验**（共享池已有 + 玩家档案已有 + 历史案例可选） | 共享池/档案已注入 setup；历史案例只能进 user 动态段 | 案例检索破坏 user 段缓存（烧 token） | ★★★ |
| **网络玩家分析经验**（人工整理条目：角色×套路×适用场景） | 同规则书，静态注入 | 零破坏 | ★★★★ |

**关键结论**：用户"减少幻觉"诉求的最高性价比点是**规则书静态注入**——setup 一次性、同局稳定、零 token 成本、直接约束"角色能力边界/可执行动作/发言红线"。历史案例 RAG（动态检索）收益不确定且烧 token，作 live 可选项。

## 七、建议落地顺序（按用户诉求重排）

```
Phase 0  补依赖：pyproject 加 faiss-cpu/rank_bm25（或纯 BM25 方案）+ 验证 embeddings live 可用
Phase 1  规则知识库 + setup 静态注入   ← 直接治幻觉，零缓存破坏，最先做
Phase 2  检索管线统一 + 相关性门控     ← 三路收敛为 retrieve→敏感过滤→门控→注入
Phase 3  离线评测集                   ← 从 29163 节点采样，recall@k/MRR 定阈值
Phase 4  工作流：玩家侧 trace 包装（不重写 act）→ 说书人声明式试点
```

> 与原计划差异：原计划 Phase 3 先做说书人裁决工作流化；现按用户诉求把**玩家侧 trace 包装**提前，说书人声明式试点保留但降为 P2 试点。

## 八、融入红线（核查补充）

在原 §4 四条红线基础上补充：

1. **前缀缓存（细化）**：规则/经验注入只放 setup 期 `stable_context`，绝不在 `act()` 内动态重算；动态检索（若启用）只进 user 末条 dynamic_context，并接受 token 成本
2. **信息隔离（细化）**：历史对局案例检索尤其危险——可能携带他局私密信息（真实身份/队友名单），注入前必须过 `MemoryToolsLike.is_sensitive`
3. **mock/live 差异**：RAG 若依赖 embeddings API，mock 测试会空转——必须有纯本地兜底（BM25），否则 480+ 单测与 9 gate 无法稳定通过
4. **"网络玩家分析经验"是新知识源**：项目无现成语料，需人工/半自动整理成结构化条目（角色 × 套路 × 适用场景），技术上复用 Phase 1 索引管线；整理时须注意**来源合规**（不搬运受版权保护的教程原文，只沉淀通用打法要点）
5. **工作流化不改变行为**：trace/声明式化不得改变 `act()` 的草稿复用、前缀缓存、超时预算与 mock 行为——以既有 480+ 单测为回归门禁
